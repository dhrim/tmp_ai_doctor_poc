### 4.2 main 보호

- **main에 직접 커밋하지 않는다 — agent도 사람도.** 작업은 브랜치/worktree에서 하고 PR로 올린다.
- **커밋은 agent가 한다.** 사람에게 커밋을 대신 해 달라고 넘기지 않는다.
- **push는 사람이 한다.** agent의 실행 환경에 GitHub 자격증명이 없기 때문이다 (2026-07-31 실측). 자격증명이 확보되면 push도 agent가 맡는다.
- **머지는 사람만 한다.** agent는 PR 생성까지.
- **머지 단위는 커밋이 아니라 작업 묶음이다** (2026-07-31 결정). 사람은 커밋마다 머지하지 않는다. 하나의 작업 묶음(예: 셋업 완료, 요구사항 정의 마감, 한 기능의 구현·검증 완료)이 끝났을 때 그 브랜치를 통째로 머지한다. 따라서 브랜치는 여러 커밋을 담은 채로 유지되며, 중간 커밋 상태로 사람을 부르지 않는다.
- 작업 묶음이 끝나면 controller가 머지 요청을 한 번에 올린다. 무엇이 끝났고 무엇을 검증했는지 요약해서 전달한다.
- 브랜치 이름: `<역할>/<태스크ID>-<요약>` (예: `verifier/T-3107-요구사항v0.3`). Vibe Kanban이 자동 생성하는 `vk/...` 브랜치는 그대로 둔다.
- 한 태스크에 활성 구현 브랜치는 하나만 둔다. 겹치는 파일을 건드리는 태스크는 controller가 순서를 정한다.
- PR 본문에는 태스크 ID, 입력 문서 버전, 검증 결과 링크를 넣는다.

### 4.2.1 GHES 개설 전 절차 (2026-07-31~)

**셋업 기간에는 임시 원격 레포 `tmp_ai_doctor_poc` 를 써서 PR 흐름을 그대로 검증한다** (§2.1). 즉 브랜치 push → PR 생성 → 사람 리뷰·머지를 실제로 돌린다. 이때 §5.3의 공개 레포 반입 금지를 지킨다.

원격을 쓸 수 없는 상황에서는 다음 로컬 절차로 대체한다.

- agent는 브랜치와 `work/<태스크>/HANDOFF_<태스크ID>.md` 를 만들고 멈춘다. HANDOFF에는 브랜치명, head commit SHA, 변경 파일 목록, 시험 결과, 검토 요청 사항을 적는다.
- controller가 사람에게 로컬 리뷰 대기를 알린다.
- 사람은 `git diff main..<브랜치>` 로 검토하고 직접 통합한다. 이 통합이 머지에 해당하며 사람만 수행한다.
- **HANDOFF에는 다음이 모두 있어야 한다.** PR이 없으므로 이 문서가 유일한 감사 증거다.

  | 항목 | 내용 |
  |---|---|
  | 브랜치·SHA | 브랜치명, head commit SHA |
  | 변경 | 변경 파일 목록, 시험 결과 |
  | 검토 | 리뷰어, 리뷰 일시, 비교 기준, 실행한 검토 명령, 검토한 diff의 저장 경로 또는 식별자 |
  | 판정 연결 | 검증 합격 SHA, 통합 대상 SHA |
  | 결과 | 승인 또는 반려, 승인 ID, 통합 결과 commit |

- **통합 후 사람이 HANDOFF에 통합 결과 commit을 추가한다.** 이 기록이 없으면 로컬 리뷰를 완료로 보지 않는다.
- 이 기간 §7.6의 "PR 리뷰"는 "HANDOFF 기반 로컬 리뷰"로 읽는다.
- **GHES가 개설되면** 원격 URL·인증·PR 생성 절차·필수 체크를 문서화하고 PR 기반 DoD를 활성화한다.

### 4.3 기존 파일 수정 허용 범위

- **코드·스크립트·설정 파일은 브랜치/worktree에서 기존 파일을 수정한다.** 버전 접미사(`_01`)를 붙여 파일을 늘리지 않는다. 이력은 git이 보존한다.
- **불변 기록물(§4.4)은 덮어쓰지 않는다.** 새 버전 파일 또는 새 노션 페이지로 만든다.
- 파일 삭제·이름 변경은 요청서에 명시되었거나 사람 승인을 받은 경우에만 한다.

### 4.4 불변 기록물

다음은 한번 작성되면 수정·삭제하지 않는다. 갱신이 필요하면 새 버전을 만든다.

- `work/` 의 요청·결과 파일 (`TASK_REQUEST_*`, `VERIFY_REQUEST_*`, `RESULT_*`, `VERIFY_RESULT_*`, `EXEC_RESULT_*`, `REMEDIATION_*`)
- **예외 하나 — `HANDOFF_<태스크ID>.md`.** GHES 개설 전 임시 감사 문서이므로, agent가 최초 작성한 뒤 **사람이 리뷰·승인·통합 결과 commit 항목만 사후 보강할 수 있다.** 보강 이력은 git 이력으로 남기고, 그 밖의 기존 내용은 덮어쓰지 않는다.
- 노션의 요구사항·설계·검증 결과·결정 로그 페이지
- 승인 기록

### 4.5 카드 실행의 전제 — 기준 commit

**Vibe Kanban은 지정된 기준 브랜치의 커밋에서 worktree를 만든다.** 커밋되지 않은 변경과 untracked 파일은 agent에게 전달되지 않는다. 카드로 작업을 시키기 전에 입력물(요청서·지침·코드)이 **커밋되어 있는지 반드시 확인한다.** (2026-07-31 실측 확인)

**검증 카드는 main이 아니라 검증 대상 브랜치의 head commit을 기준으로 만든다.** 그러지 않으면 미통합 구현물을 Verifier가 볼 수 없고, 보이게 하려고 먼저 통합하면 "검증 합격 전 통합 금지"를 위반한다.

- Planner는 `VERIFY_REQUEST` 에 대상 브랜치명과 **검증 대상 commit SHA**를 기록한다.
- **Vibe Kanban은 브랜치를 기준으로 worktree를 만든다. 임의 SHA 지정은 보장되지 않는다.** 따라서 controller는 그 SHA에 **검증 기준 브랜치** `verify/<태스크ID>/<짧은SHA>` 를 만들고, 그 브랜치를 카드의 기준 브랜치로 지정한다. 구현 브랜치가 검증 중에 전진해도 검증 기준 브랜치는 움직이지 않는다.
- **Verifier는 시작 직후 HEAD가 요청서의 SHA와 일치하는지 확인한다.** 다르면 검증하지 않고 반송한다.
- Verifier는 그 SHA를 읽기 전용 기준으로 검증하고 결과에 SHA를 명시한다.
- **검증 후 대상 commit이 바뀌면 기존 합격은 무효다.** 재검증한다.
- 사람은 검증이 합격한 SHA를 포함한 브랜치만 통합한다.

### 4.6 레포 구조

```
README.md / AGENTS.md / CLAUDE.md / CODEX.md / GEMINI.md / HUMAN.md   규칙 문서
work/     태스크별 핸드오프 (요청 → 결과)
tools/    스크립트
src/      시스템 코드 — 최초 구현 태스크가 생성한다 (현재 없음)
```

### 4.7 산출물을 어디에 두는가

- **프로젝트 지식(요구사항·설계·결정·작업 기록)의 정본은 노션이다.** 레포에 사본을 두지 않는다.
- **예외: agent 실행 계약이자 감사 증거인 `work/` 의 요청·결과 파일은 레포에 둔다.** 노션에는 결정과 요약을 남기고 해당 파일 또는 PR을 링크한다. 같은 본문을 양쪽에 복제하지 않는다.
- 코드·스크립트는 레포.
- 파일이 크면 임의로 올리지 말고 사람에게 묻는다.

**노션 문서 제목 규칙**

```
YYYY/MM/DD <제목> [by AI]
```

- **제목 앞에 날짜를 적는다.** 형식은 `YYYY/MM/DD`. 특정 시점의 작업·기록·결과가 아닌 상시 참조 문서(정본 대장, 용어집 등)는 예외로 날짜를 생략할 수 있다.
- **agent가 만든 문서는 제목 끝에 ` by AI` 를 붙인다.** 사람이 쓴 문서와 제목만 보고 구분되어야 한다. 사람이 이어서 크게 손본 문서라도 최초 작성이 agent면 표시를 유지한다.
- 예: `2026/07/31 요구사항 검증 결과 by AI`
- 레포 파일에는 두 규칙을 적용하지 않는다 — 파일명에 날짜가 있고 git 이력에 작성자가 남기 때문이다.

## 5. 데이터·보안 (완화 불가)

### 5.1 hCDM·환자정보

- hCDM은 read-only이며 PHI의 프록시로 취급한다. 승인된 내부 격리 환경과 최소권한 계정에서만 접근한다.
- **원문 행, 환자 단위 값, 재식별 가능한 희귀 조합을 외부로 내보내지 않는다.** 외부에는 외부 LLM·MCP·브라우저·로그·스크린샷·이슈·PR·채팅이 모두 포함된다.
- 반출은 집계·비식별 결과에 한하며, 재식별 위험을 검토한 뒤 사람 승인을 받는다.
- 노출이 의심되면 **즉시 작업을 중지한다.** 스스로 판단해 계속하지 않는다. 이후 절차는 다음 순서다.

  `작업 중지 → controller가 사람에게 즉시 통보 → 사람이 사고 ID 발급(노션 결정 로그) → 자격증명 비활성화 → 영향 범위와 로그 보존 → 사람 조사 → 재개 승인(승인 ID)`

- hCDM 접근·쿼리·반출은 감사로그에 남긴다. 항목: 시각, 수행자, 목적, 대상, 반출 여부, 승인 ID. 보존기간·접근권한의 기본값은 §5.5와 같고, 셋업 완료 전에 확정한다(§9.1).
- **hCDM 설치나 접근이 막히면 상태를 `환경차단`으로 전환하고 사람 판단을 요청한다** (§7.9). 허용되는 임시 경로는 합성 데이터·공개 샘플·스키마 mock뿐이다. **이 결과는 hCDM 기반 성능시험을 대체하지 않으며 합격 근거가 되지 않는다.**

### 5.2 제품 코드

- 제품(구축 시스템) 코드에 외부 상용 LLM API(Claude/GPT/Gemini 등)를 넣지 않는다. 내부 서빙 Gemma만 사용한다. 개발 도구로 쓰는 것은 허용한다.
- 이 제약을 우회하는 구현을 제안하지 않는다.

### 5.3 레포에 넣지 않는 것

토큰·키 등 비밀정보, 대외비 원문(계획서·연차보고서), hCDM 데이터 일체, 마스킹되지 않은 실행 로그.

**셋업 기간의 원격 레포(`tmp_ai_doctor_poc`)는 공개 레포다.** 위 금지 항목에 더해, 과제 고유의 설계·요구사항 본문도 올리지 않는다. 셋업 검증용 합성·더미 산출물과 규칙 문서만 올린다.

### 5.4 외부 도구·의존성

- 외부 CLI·MCP·패키지는 **버전을 고정해서** 쓴다. `npx -y <버전 없는 패키지>` 실행을 금지한다.
- 새 도구·MCP를 등록하기 전에 그 도구가 읽는 데이터 범위, 전송 대상, 자격증명 범위를 확인하고 사람 승인을 받는다.
- 비공식 내부 API 사용은 실패 시 공식 API로 전환할 경로를 함께 준비한다.

**승인된 외부 도구 목록** — 이 표에 없는 도구는 승인되지 않은 것이다.

| 도구 | 버전 | 설치 명령 | 무결성 확인 | 허용 데이터 범위 | 승인 ID | 상태 |
|---|---|---|---|---|---|---|
| Notion MCP (`@notionhq/notion-mcp-server`) | 미고정 | 셋업 시 확정 | 셋업 시 확정 | 노션 페이지 읽기 | 없음 | **미승인.** 무버전 `-y` 등록 상태. 셋업 완료 전 고정 버전으로 재등록 필요 |

**이 표에 없는 MCP·CLI·패키지는 agent가 설치하거나 실행하지 않는다.** 표는 셋업 완료 전까지 최소 도구 세트로 확정한다.

### 5.5 실행 로그

- 원문 실행 로그는 레포 밖에 저장하고 토큰·환자정보·대외비를 마스킹한다.
- **다른 agent·다른 PC가 이어받을 수 있어야 한다.** 인수인계에 필요한 로그는 마스킹한 재현 로그로 `work/<태스크>/` 에 남긴다. 개인 경로에만 두면 문맥 유지 의무(`AGENTS.md` A3)를 위반한다.
- 결과 문서에는 원문 대신 요약, 로그 식별자, 보존 만료일을 남긴다.
- 원문 로그는 승인된 내부 위치에 저장하고 **태스크 ID로 식별**한다. `work/` 에는 원문 경로가 아니라 로그 ID, 보존 만료일, 마스킹 재현 로그를 남긴다.
- 정책은 셋업 완료 전에 확정하되(§9.1), **그때까지 아래 기본값을 적용한다.**

  | 항목 | 기본값 |
  |---|---|
  | 원문 보존기간 | 30일 |
  | 접근권한 | 사람 + controller |
  | 최대 크기 | 태스크당 100MB |
  | 폐기 | 사람이 승인한 스크립트 또는 수동 삭제 |
  | `work/` 저장 대상 | 민감정보를 제거한 재현 로그만 |

## 6. 사람 전용 권한 (완화 불가)

다음은 **사람만** 수행한다. agent는 수행하지 않는다. 절차는 `HUMAN.md`.

- git 머지 (agent는 PR 생성까지)
- 미결 사항 결정 — 기능 범위, 대상 질환, 우선순위
- 잠정 기준의 확정 (§7.4)
- 비용 발생·클라우드 배포 승인
- 이터레이션 중단 판단
- 대용량 파일의 저장 위치 판단
- 계정·자격증명 입력, 외부 기관 대응, 대외 문서 제출
- 규칙 문서 변경의 최종 승인 (§9)

**예외 한 가지:** 태스크 추가·수정·삭제는 **사람 또는 controller**가 수행한다. 다른 agent는 수행하지 않는다.

## 7. 일하는 방식

### 7.1 Plan-Do-Verify

**셋업 완료 선언(§9.1) 이후 시작되는 모든 프로젝트 태스크는 Plan-Do-Verify로 진행한다. 예외 없음.** 문서·코드·설정 전부. 검증 통과가 완료의 조건이다. 셋업 기간의 작업은 이 상태 모델의 적용 대상이 아니며, §9.1의 셋업 완료 체크리스트로 일괄 검증한다.

개발은 **PEV-E**(Planner–Engineer–Verifier + Executor). **검증자는 생산자와 다른 회사 모델**이 수행한다. 이 규칙은 사후 기재가 아니라 **요청서 단계에서 강제한다.** `TASK_REQUEST`·`RESULT_*`에는 생산자의 역할·회사·모델·실행 식별자를 적고, `VERIFY_REQUEST`에는 그 값을 복사해 넣는다. Verifier는 시작 직후 자기 회사가 생산자와 다른지 확인하고, **정보가 없거나 회사가 같으면 검증하지 않고 반송한다.** 방법론·산출물을 시뮬레이션·평가하는 역할을 둘 경우 **생산자·검증자·시뮬레이터를 서로 다른 회사 모델**로 둔다. 결과 문서에 각자의 회사·모델명과 실행 식별자(세션 ID 또는 카드 ID)를 적는다. 회사가 같으면 검증을 시작하지 않는다.

### 7.2 상태 모델

```
계획대기 → 구현중 → 구현완료 → 검증중 → (재작업 | 기준승인대기 | 승인대기) → 사람통합 → 완료
```

| 전이 | 주체 | 필요 증거 |
|---|---|---|
| 계획대기 → 구현중 | Planner | 태스크 ID, 요청서, 합격 기준 |
| 구현중 → 구현완료 | Engineer | 산출물, `RESULT_*.md`, 단위시험 통과 |
| 구현완료 → 검증중 | Planner | `VERIFY_REQUEST_*.md`, 기반 문서 버전 고정 |
| 검증중 → 재작업 | Verifier | `VERIFY_RESULT_*.md`, 판정 불합격/조건부 불합격 |
| 검증중 → 기준승인대기 | Verifier | 판정 보류(기준 부재) + 기준안 제안 |
| 기준승인대기 → 검증중 | Planner | 사람 승인 ID를 반영한 새 요청서 |
| 검증중 → 승인대기 | Verifier | 판정 합격 + 검증 대상 commit SHA |
| 승인대기 → 사람통합 | 사람 | 리뷰 완료, DoD(§7.6) 충족 확인 |
| 사람통합 → 완료 | 사람 | 통합 완료, PMS 상태 갱신 |

위 흐름을 벗어나는 상태는 §7.9에 정의한다: `사람판단대기`, `환경차단`, `성능미달`, `결정대기`.

Executor는 승인된 절차의 **실행자**이며 판정 권한이 없다. 판정은 Verifier가 한다.

**Executor 투입 경로.** Planner가 요청서에 `executor_required: true` 와 실행 범위를 명시한 태스크만 Executor를 쓴다. Executor는 같은 `work/<태스크>/` 에 `EXEC_RESULT_<대상버전>.md` 를 남기고, 실행 환경·명령·로그 ID·산출물 위치·성공 여부만 기록한다(판정 없음). **Verifier는 이를 판정 근거로 삼되, `executor_required: true` 인데 `EXEC_RESULT_*` 가 없으면 재현 불가로 판정한다.**

### 7.3 결함 등급과 판정

| 등급 | 정의 |
|---|---|
| **중대** | 안전·보안·법규 위반, 데이터 손상, 핵심 기능 실패, 거짓 완료 |
| **주요** | 요구사항 불충족, 재현 불가, 추적성 단절 |
| **경미** | 결과에 영향 없는 품질 문제 |

- 중대 1건 이상 → **불합격**
- 중대 0건, 주요 미해결 1건 이상 → **조건부 불합격**
- 중대·주요 0건이고 모든 필수 기준 충족 → **합격**

**조건부 불합격은 완료가 아니다.** 통합할 수 없다.

네 번째 결과 상태로 **판정 보류**가 있다. 합격 여부를 매길 기준 자체가 없을 때 쓴다. 결함 판정이 아니며 상태는 `기준승인대기`로 간다 (§7.2·§7.4).

### 7.4 합격 기준의 출처와 확정 권한

- 기준의 출처는 계획서와 거기서 도출된 요구사항이다.
- 기준이 없으면 **Planner가 근거와 함께 '제안' 상태의 기준을 작성**한다.
- Verifier는 기준안을 제안할 수 있으나 **확정하지 않으며**, 기준 부재를 불합격 사유로 삼지 않고 "기준 부재"로 지적한다.
- 제품 범위·안전·성능·비용에 영향을 주는 기준은 **사람 승인 후 '확정'** 상태가 된다. 승인 전 항목은 판정 보류로 표시한다.

### 7.5 승인 규약

- 승인 1건마다 **승인 ID**를 부여하고 노션 결정 로그에 남긴다. 요청서·결과 문서에 그 ID를 인용한다.
- 승인 전에는 §6 항목, 외부 배포, 비용 발생, 민감데이터 접근, 범위 변경을 실행하지 않는다.
- **읽기 전용 조사와 로컬 무비용 시험은 별도 금지 지시가 없으면 승인 없이 수행한다.** 모든 것을 멈춰 세우지 않는다.

### 7.6 완료 정의 (DoD)

다음을 모두 충족해야 완료다.

1. 요구사항 ID 전수 추적
2. 빌드 성공, 자동시험 통과
3. 비밀정보·환자정보 혼입 검사 통과
4. 실행·롤백 절차 확인
5. Verifier 판정 '합격'
6. 사람의 PR 리뷰와 머지

**예외 통합은 경미 결함 또는 비필수 기준의 유예에만 허용**하며, 사람의 위험수용 승인 ID와 만료일을 남긴다. **중대 결함, 보안·법규 위반, 환자정보 위험, 핵심 기능 실패, 그리고 조건부 불합격·불합격 판정은 위험수용 승인으로도 통합할 수 없다.**

### 7.7 검증 이터레이션

- 최초 검증을 **1회차**로 세고, 최대 **5회**.
- 요청서와 결과에 `iteration: n/5` 를 기록한다.
- 결함에는 고유 결함 ID를 부여한다. 동일 요구사항·동일 원인·동일 조치안이면 동일 쟁점이다.
- 같은 결함 ID가 **연속 두 결과에서 미해결이면 자동으로 `사람판단대기` 상태로 전환**한다 (§7.9).
- 5회 도달 시 추가 실행하지 않고 사람에게 올린다.

### 7.8 문서화 수준

고정 서식은 강제하지 않는다. 다만 **모든 요청서**에는 목적·범위·입력 문서와 버전·**추적 ID**·합격 기준·검증 방법·산출물 경로·승인 필요 여부·`executor_required`·생산자 정보(회사·모델·실행 식별자)를, **모든 결과 문서**에는 변경 요약·재현 절차·시험 결과·미결 사항·다음 담당을 포함한다.

추적 ID는 제품 구현이면 **요구사항 ID**, 운영·도구·규칙·장애 대응이면 **결정 ID 또는 내부 통제 ID**를 쓴다. 해당 ID가 없으면 Planner가 태스크 생성 전에 발급한다.

목적은 워킹 시스템, 성능, 기준을 통과한 결과물, 필요할 때 참조 가능한 문서다. 사전에 모든 것을 문서화하고 시작하는 방식은 쓰지 않는다.

### 7.9 예외 상황과 상태

정상 흐름(§7.2)을 벗어나는 사건은 아래 상태로 전환하고, 표의 결정 항목 중 하나를 사람이 고른다. **어느 경우에도 agent가 스스로 판단해 진행하지 않는다.**

| 상태 | 전환 조건 | 기록할 것 | 사람이 고를 결정 |
|---|---|---|---|
| `사람판단대기` | 동일 결함 ID가 연속 두 결과에서 미해결, 또는 이터레이션 5회 도달 | 결함 ID, 두 결과 링크, 쟁점 요약 | 수정 지시 / 기준 변경 / 위험수용 가능 여부 / 태스크 중단 |
| `환경차단` | hCDM 설치·접근 차단, 도구·계정 미확보로 작업 불가 | 차단 지점, 시도한 것, 영향 태스크, 일정 영향 | 환경 복구 / 합성 데이터 대체 / 일정 변경 |
| `성능미달` | 성능시험에서 기준 미달 | 미달 항목, 기준값과 실측값, 재현 로그 ID, 원인 가설, 개선 예상 시간 | 재시험 / 범위 축소 / 기준 변경 제안 / 일정 변경 / 리스크 수용 불가 |
| `결정대기` | 사람 승인·결정이 1영업일 이상 지연 | 대기 중인 결정, 영향 태스크, 일정 위험 | (해소되면 원 상태로 복귀) |

**결정 후 복귀 전이.** 사람이 결정하면 아래 상태로 돌아간다. 모든 복귀에 승인 ID 또는 결정 로그 ID를 남긴다.

| 상태 | 사람의 결정 | 복귀 상태 |
|---|---|---|
| `사람판단대기` | 수정 지시 | `재작업` |
| | 기준 변경 | `기준승인대기` |
| | 위험수용 (§7.6 제한 통과 시에만) | `승인대기` |
| | 태스크 중단 | `완료(중단)` |
| `환경차단` | 환경 복구 | 차단 직전 상태 |
| | 합성 데이터 대체 | 새 요청서 발행 후 `구현중` 또는 `검증중` |
| `성능미달` | 재시험 | `검증중` |
| | 범위 축소 / 기준 변경 제안 | `기준승인대기` |
| | 일정 변경 | 차단 직전 상태 유지 |
| | 리스크 수용 불가 | `사람판단대기` |
| `결정대기` | 결정 완료 | 원 상태 |

- **상태는 두 축으로 관리한다.** 원인 상태는 `primary_status`, 사람 결정 지연은 `blocking_status: 결정대기`. 한 태스크는 원인 상태 하나와 차단 상태 하나를 동시에 가질 수 있다.
- **위험수용은 §7.6의 제한을 받는다.** 중대 결함, 보안·법규 위반, 환자정보 위험은 위험수용 대상이 아니다.
- **기준 변경은 승인 ID와 근거가 없으면 적용하지 않는다.**
- 성능시험은 일정상 1회가 원칙이므로(§3), `성능미달` 전환 시 controller는 즉시 사람에게 올리고 노션 프로젝트 현황과 PMS 일정을 갱신한다.

### 7.10 모델 교체와 회귀

의료특화 Gemma 수령 전에는 일반 Gemma로 구현한다(§3). 이때 **모델에 의존하는 기능에는 `MODEL-PENDING` 추적 ID를 붙인다.**

- 의료특화 Gemma 수령 후 그 ID가 붙은 기능은 **성능·안전 회귀시험을 필수로 재수행**한다.
- **일반 Gemma로 얻은 결과는 최종 성능시험 합격 근거로 쓰지 않는다.**

### 7.11 규칙 오해의 기록

agent가 규칙을 잘못 해석해 잘못된 산출물을 만들었으면, 제품 결함과 **분리해서** `RULE-MISREAD` 기록을 남긴다.

- Verifier는 산출물 결함과 지침 모호성을 따로 판정한다.
- controller는 해당 지침의 수정 필요 여부를 개선 라운드 대기 목록(§9.2)에 넣는다.
- **동일한 오해가 반복되면 작업을 중단하고 사람 판단을 받는다.**

### 8.1 PMS와 Vibe Kanban의 경계 (2026-07-31 결정)

- **PMS가 태스크의 정본이다.** agent가 하는 일과 사람이 하는 일을 **모두** PMS에 등록한다. 태스크 ID, 담당, 상태, 일정은 PMS의 값이 유일한 사실이다.
- **Vibe Kanban은 오로지 agent 실행 도구다.** 태스크를 관리하지 않고, 카드의 상태는 진행 상태를 뜻하지 않는다. 카드는 실행 흔적일 뿐이다.
- 카드 제목은 `<PMS 태스크 ID> <요약>` 으로 시작한다. PMS 태스크 ID 없는 카드를 만들지 않는다.
- 카드가 끝나면 **controller가** 결과를 PMS 태스크 상태와 노션에 반영한다. agent는 카드 안에서 PMS를 고치지 않는다 (태스크 변경 권한은 README §6).

## 9. 규칙의 시행과 변경

### 9.1 시행 시점

**2026-07-31 현재는 셋업 기간이며 프로젝트는 아직 시작되지 않았다.** 이 규칙 v1.0은 셋업 완료 후 **첫 태스크부터** 적용한다. 셋업 기간의 작업(도구 연동, 지침 문서 작성, 환경 구성)은 태스크 등록·검증 이터레이션 대상이 아니며, 개인 워킹 경로의 작업기록으로만 남긴다.

셋업 완료 선언은 사람이 한다. **아래 전 항목에 증거가 있을 때만 선언할 수 있다.** 각 항목에는 증거 파일 경로 또는 노션 기록 링크를 붙인다. **하나라도 미완료면 프로젝트 태스크를 만들지 않는다.** 단 체크리스트를 완료하기 위한 작업은 셋업 작업으로 수행한다. 선언 이후로는 §7.1이 예외 없이 적용된다.

**셋업의 목적은 agent 간 코워크가 성립하는지 확인하는 것이다** (2026-07-31 결정). 특정 모델이나 인프라의 완비가 아니라, 요청 → 작업 → 검증 → 통합이 서로 다른 agent 사이에서 끊기지 않고 도는지를 본다.

- [ ] controller(Claude)와 Verifier(Codex) 실행 수단 확인 — 각 1건 성공
- [ ] 두 agent의 워킹 경로 존재 (`D:\workspace\claude`, `D:\workspace\codex`)
- [ ] PMS 접근 확인, 노션 정본 page_id 기입 (§2.1)
- [ ] 임시 원격 레포 연결과 push 성공 (§2.1·§4.2.1)
- [ ] **PR 1건을 실제로 만들고 사람이 머지까지 완료**
- [ ] 검증 카드가 지정 commit 기준으로 생성되는지 실측 확인 (§4.5)
- [ ] **문서 태스크 1건으로 왕복 1회 성공** — Planner(Claude)가 요청서 발행 → Verifier(Codex)가 검증 → 결과 회수 → PR → 사람 머지. 구현 단계는 넣지 않는다. 생산자와 검증자의 회사가 달라야 한다 (§7.1)
- [ ] 왕복의 상태·기록·판정이 새 세션 agent에게 구두설명 없이 인수됨

**구현이 포함된 종단간 리허설은 셋업 완료 조건이 아니다** (2026-07-31 결정). 2~3일간 코딩 작업이 없고 Engineer(Gemini)가 대기 중이므로, 셋업에서는 **구현 없는 왕복**으로 agent 간 코워크 성립만 확인한다. 구현을 포함한 리허설은 Engineer 투입 직전에 수행한다.

**셋업 완료 후로 이월하는 항목** — 아래는 셋업 완료를 막지 않는다. 해당 역할이나 데이터를 실제로 쓰기 시작하기 전까지 닫으면 된다.

| 이월 항목 | 언제까지 |
|---|---|
| Gemini 워킹 경로·실행 수단 | Engineer를 실제로 투입하기 전 |
| 구현 포함 종단간 리허설 | Engineer 투입 직전 |
| 외부 도구·MCP 고정 버전 승인 (§5.4) | agent가 노션 MCP나 새 외부 도구를 쓰기 전 |
| 보안 사고 절차·감사로그 정책 확정 (§5.1) | hCDM에 접근하기 전 |
| 로그 보존·공유 정책 확정 (§5.5) | 기본값 적용 중. 공용 로그 저장소를 도입할 때 |
| GHES 개설과 정식 레포 이전 | 프로젝트 시작 시 |

**셋업 기간의 지침 점검·개선은 프로젝트 태스크가 아니다.** PMS 등록, Vibe Kanban 카드, PR·통합 의무의 대상이 아니며, 개인 워킹 경로의 작업기록으로 남긴다. 다만 셋업 완료 선언 전에 **점검 회차별 판정과 결함 반영 여부를 노션 "지침 점검 로그" 페이지에 요약**한다. 이 페이지가 점검 이력의 정본이며, page_id는 §2.1에 기입한다. 확보 전까지는 controller의 작업기록이 임시 보관처다.

### 9.2 검증 후 개선 라운드

Verifier 결과를 받아 문서·산출물을 고치는 국면을 **개선 라운드**라 한다. 절차는 다음과 같다.

1. **결함 전수 대응표를 만든다.** Planner가 같은 `work/<태스크>/` 에 `REMEDIATION_<대상버전>_iter<n>.md` 를 새로 만든다. 불변 기록물이며 덮어쓰지 않는다. 결함 ID마다 `반영 / 거부 / 보류` 중 하나와 이유, 관련 commit 또는 문서 위치, 필요한 승인 ID를 적는다. 조용히 넘어가는 항목이 없어야 한다. **거부는 사람 승인**을 받는다. 재검증 요청서는 이 대응표를 입력 문서로 포함한다.
2. **그 사이 누적된 결정을 함께 반영한다.** 검증이 도는 동안 대화·회의에서 정해진 사항, controller가 보류해 둔 지침 반영 대기 항목을 이 라운드에서 문서에 넣는다. 검증 결함만 고치고 끝내지 않는다.
3. 변경 요약(무엇을 왜 바꿨는지)을 남긴다.
4. **반영했으면 반드시 재검증한다.** 개선 라운드의 결과물은 검증 없이 완료가 되지 않는다 (§7.1). 재검증 요청서에 `iteration: n/5` 를 기록한다.

controller는 대화에서 정해졌지만 아직 문서에 들어가지 않은 사항을 **지침 반영 대기 목록**으로 유지하고, 개선 라운드마다 비운다. 대기 목록에 오래 남은 항목은 유실된 것으로 본다.

### 9.3 변경 절차

- 규칙 변경은 별도 태스크와 PR로 제안하고, 변경 이유·영향 문서·시행일을 기록한다.
- **다른 회사 모델이 모순·보안·실행 가능성을 검증**하고, **사람이 승인·머지**한다. controller가 단독으로 확정하지 않는다.
- 진행 중인 태스크에는 시작 당시의 규칙 버전을 적용한다. 단 **보안 규칙(§5) 강화는 즉시 적용**한다.
- 변경 시 각 문서 머리의 규칙 버전·시행일을 갱신한다.

## 11. 소통과 추적

### 11.1 왜 controller를 거치는가 — 추적성

이 프로젝트의 모든 지시·판단·산출물은 **나중에 되짚을 수 있어야 한다.** 사람이 실행 agent에게 직접 지시하면 그 지시는 어디에도 남지 않고, 다른 실무자와 함께 일할 때 무엇이 왜 그렇게 됐는지 복원할 수 없다.

그래서 지시는 controller 한 곳을 통과시킨다. controller를 지나면 지시가 **git 이력, 작업 문서, controller의 대화 이력** 세 곳에 흔적을 남긴다. 이것이 controller 단일 창구 규칙의 목적이며, 규칙보다 목적이 우선한다 — **어떤 경로로 일하든 추적 가능해야 한다.**

### 11.2 규칙

- 모든 소통·산출물은 한글.
- **사람은 controller agent와만 직접 소통한다.** 다른 agent에 대한 지시는 controller가 지침 문서와 작업 요청으로 전달한다. 같은 지시를 사람이 두 번 하지 않게 하는 것이 controller의 책임이다.
- **controller는 받은 지시를 그 자리에서 문서로 승격한다.** 미루지 않는다.

| 받은 것 | 남기는 곳 |
|---|---|
| 작업 방식·규칙에 대한 지시 | 지침 문서 변경 제안 (§9) |
| 수행할 일 | 태스크 등록 + `work/` 요청서 |
| 판단·선택·승인 | 노션 결정 로그 (승인 ID) |
| 배경·맥락 | 노션 작업 페이지 |

- **문서화되지 않은 지시는 없던 것으로 취급한다.** 구두로만 전달된 규칙은 유지되지 않는다.
- 실무자가 늘어도 방식은 같다. 각자 자기 controller를 통해 지시하고, 기록은 공용 저장소(레포·노션)에 남긴다. 개인 PC나 특정 대화창에만 있는 문맥은 문맥으로 인정하지 않는다.
- **예외:** 보안 사고, 환자정보 노출 의심, 비용 급증, 서비스 장애, controller 접근 불가 — 이때 사람은 실행 중인 agent를 직접 즉시 중지시킬 수 있다. 중지 후 사후 기록은 남긴다.
- **controller가 처리량 병목이 되면** — 1영업일 안에 요청서 발행·결과 회수·PMS와 노션 반영을 못 할 것으로 보이면 — 사람이 **보조 controller**를 승인 ID로 지정할 수 있다. 권한 범위와 유효기간을 기록하고, 최종 추적성 점검은 원 controller가 한다.
- **controller 접근 불가가 1세션 이상 이어지면** 사람이 임시 controller와 유효기간을 승인 ID로 지정한다. 임시 controller는 인수인계 체크리스트를 받은 뒤 권한을 행사하고, 원 controller 복귀 시 종료를 기록한다.
- **사람의 승인·결정이 1영업일 이상 지연되면** controller가 `결정대기`로 표시하고 영향 태스크와 일정 위험을 기록한다(§7.9). **2영업일 이상 부재가 예상되면** 사람이 사전에 대리 결정자·권한 범위·유효기간을 승인 ID로 지정한다. 대리 결정자가 없으면 비용·보안·범위·성능 기준 관련 작업은 진행하지 않는다.
- controller 교대 시 인수인계 문서를 남기고 `CLAUDE.md` 등 역할 문서를 갱신한다.
